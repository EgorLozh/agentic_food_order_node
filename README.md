# agentic-food-order-node

Бескаркасный бот заказов (Telegram + LLM-агент), переписанный на Node.js так, чтобы **не дублировать
логику каркаса**: заказ пишется кодом FeedMer (`db.saveOrder` / `db.addItem` / `db.addChatId`),
который подключается как библиотека. FeedMer и graphEditor не изменяются.

## Быстрый старт

```bash
npm install
cp .env.example .env      # DB_URL / DB_LOGS_URL как у FeedMer, FEEDMER_LIB_DIR — путь до чекаута FeedMer
npm run check:feedmer     # окружение: код каркаса, коммит, зависимости, схема БД
npm run smoke:order       # создаёт заказ кодом каркаса, читает обратно, удаляет за собой
npm run smoke:menu        # кафе и меню функциями каркаса
npm test                  # правила даты/таймзоны и меток оплаты
```

Если `smoke:order` падает на `chatids`/`pk_orders` — сначала выравнивание схемы:

```bash
psql -h localhost -U <user> -d testing -v ON_ERROR_STOP=1 -f scripts/fix-shared-db-schema.sql
```

## Как подключается код каркаса

```
src/feedmer.js
  ├─ выставляет process.env.DB_URL / DB_LOGS_URL (нужны DBlib.js до require) и TESTING
  ├─ объявляет глобалы, которые в каркасе ставит scenarios.js/index.js: logEr, timeLog, logAI, sleep
  ├─ добавляет наш node_modules в NODE_PATH (у FeedMer своего node_modules нет)
  └─ require('<FEEDMER_LIB_DIR>/DBlib.js') → тот же объект db, что у каркаса
```

Создание заказа (`src/orders/pickupOrder.js`) — вызовы каркаса: `getUserIdByTelegramChatId` →
`addNewUser` → `addChatId` → `addItem` (строка на единицу) → `saveOrder`. На нашей стороне остаются
только мелкие правила, живущие в `scenarios.js` (не импортируется целиком): дата заказа в таймзоне
кафе, маппинг оплаты в `payway_type`, `deliverysum=0` / `ASAP=false` / `deliveryTimeFinish=null`
для самовывоза.

Меню и кафе (`src/menu/feedmerMenu.js`) — тоже функции каркаса, своих SQL к `pricelist`/`cafes` нет:
`getAllCafesInfo`, `getCafeInfo` (в том числе таймзона для даты заказа), `getPricelist`,
`getActualPricelist` (только позиции из графа бота), `getItemByNameFromDB`, `getPricelistAsString`
(строка названий для промпта LLM).

## Статусы хода в черновике

Ход агента занимает несколько секунд, поэтому вместо пустого экрана клиент видит, что бот делает
прямо сейчас: `sendMessageDraft` обновляет один и тот же черновик (`draft_id` на ход) —
«Думаю…» → «Ищу в меню…» → «Проверяю состав заказа…» → «Формирую заказ…» → «Пишу ответ…».
Финальный ответ по-прежнему уходит обычным сообщением с клавиатурой: черновик при этом исчезает.

- Подписи — словарь `STATUS_LABELS` в `src/bot/draftStream.js`, ключи — имена инструментов агента.
  Агент только сообщает имя инструмента (`onProgress`), в человеческий статус его переводит бот.
  Многоточия в подписях нет: клиент рисует бегущие точки сам, иначе они дублировались.
- Перед отправкой ответа черновик получает **текст этого ответа** (`DraftStream.setText`). Иначе
  Telegram Desktop оставляет последний черновик в чате пузырём со статусом до 30 с; если текст
  черновика совпадает с текстом сообщения, клиент заменяет черновик сообщением и ничего лишнего
  не остаётся. Порядок такой: статусы → черновик с ответом → `ctx.reply` с клавиатурой.
- Стрим включается флагом `TELEGRAM_DRAFT_STREAM` (по умолчанию вкл), обновления троттлятся
  `TELEGRAM_DRAFT_INTERVAL_MS` (400 мс) и не дублируют одинаковый текст.
- Метод работает только в приватных чатах. Любая ошибка API (например, у бота не включён Forum
  Topic Mode) гасит статусы один раз с предупреждением в лог — дальше ход идёт как раньше,
  «печатает…» возвращается автоматически.

## Форматирование ответов

Ответы собираются блоками, чтобы их можно было читать в чате без разбора простыни. За это отвечают
две вещи: правила в системном промпте (`src/llm/prompt.js`, блок «Финальный ответ» + четыре эталонных
примера) и детерминированный форматтер `src/bot/format.js`, который не даёт виду зависеть от того,
как модель написала ответ:

- «•» всегда начинает новую строку — даже если модель склеила список («• A • B» → две строки);
- поля заказа («Самовывоз», «Время», «Оплата», «Телефон», «Итого», …) выносятся на свою строку,
  если модель вписала их в середину абзаца;
- перед «Итого», вопросом клиенту, блоком «Варианты:» и после списка позиций ставится пустая строка;
- 2+ пробела и лишние пустые строки схлопываются; слова, названия и цены не меняются.

Форматтер применяется в `BotService.handleText` до дописывания вариантов, поэтому и блок
«Варианты:» проходит через те же правила. Подпись кнопки считается показанной, только если стоит
отдельным словом (раньше «да» находилось внутри «Стандарт», и в блок попадало одно «нет»;
дежурная фраза «Если нужного варианта нет…» из сравнения исключается).

Проверено вживую (сценарии `happy_shaurma` и `stepwise_slots` через бенч близнеца): максимальная
длина строки в ответах 36–59 символов вместо 117–150, переносы и блоки на месте.

## Проверки

```bash
npm test            # 65 тестов: правила заказа, матчер, инструменты, агент/оркестрация на подменённой модели, статусы хода
npm run smoke:order # сквозной заказ кодом каркаса + чтение из БД + уборка
npm run smoke:menu  # кафе и меню функциями каркаса
npm run smoke:tools # скриптовая беседа без LLM: инструменты → заказ в БД
npm run smoke:agent # живая переписка агента с моделью (нужен ключ в .env)
npm run smoke:bot   # тот же сервис, что у telegraf: диалог → заказ в БД → уведомление админа
npm run smoke:draft # живая проверка статусов черновика в чате ADMIN_TELEGRAM_ID (sendMessageDraft)
npm start           # запуск бота (нужен свободный BOT_TOKEN)
npm run check:feedmer # окружение: код каркаса, коммит, зависимости, схема БД
npm run seed:pricelist 68 72  # прайс кафе из его Google-таблицы штатным писателем каркаса (db.updatePricelist)
```

Ключи моделей вписываются в `.env` (шаблон — `.env.example`): `LLM_PROVIDER` +
`DEEPSEEK_API_KEY` / `OPENAI_API_KEY` / локальная `OLLAMA_*`.

Паритет с каркасом теперь структурный: заказ пишут те же функции (`db.saveOrder`, `db.addItem`),
а не наша копия SQL, поэтому сверка «наш SQL vs SQL каркаса» из Python-версии больше не нужна.
