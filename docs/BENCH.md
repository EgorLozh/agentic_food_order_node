# Время ответа бота (прод, 194.67.124.139)

**Время ответа** — интервал от отправки сообщения клиентом до получения ответа бота. Ниже — два независимых
замера на живом проде:

1. **E2E через Telegram** — тестовый аккаунт (Telethon, `food-order-bench` из Python-проекта) отправляет боту
   @testfeedmer_bot реальные сообщения и фиксирует время ответа. Это ровно то, что видит клиент.
2. **Внутренний замер** — `npm run bench:agent` на сервере: тот же `BotService` без Telegram, зато с разбивкой
   на обращения к модели и отдельным замером чистой задержки модели.

Конфигурация: `deepseek/deepseek-flash`, кафе по умолчанию 68, трафик бота через AmneziaWG.
Сырые отчёты — `bench/reports/`.

сценарии ждут `(подтверд|подтверж)`, а бот спрашивает «Всё верно?» с кнопками «да/нет»
(так после правок форматтера). Поведение верное: заказ создаётся только после «да».

Это потому что `ADMIN_TELEGRAM_ID` — тот же тестовый аккаунт, из которого идёт замер; поэтому 3,4 c
в финале включают ожидание второго сообщения.

## Выводы

- **Время ответа делает модель, а не сервер.** Чистый ping модели 1,10 c, а обращение в агенте 2,23 c:
  каждый запрос тащит в prompt системную инструкцию, историю диалога и описания 12 инструментов.
- **Время ответа ≈ число обращений к модели × 2,23 c + ~0,1 c** на чтение/запись БД и форматирование.
  Медиана 2,5 обращения даёт 4,8–5,5 c — это и есть наблюдаемые 4,72 c по текстовым сообщениям.
- **Telegram добавляет 0,3–0,5 c** — видно по `/start` и `/cancel`, где модель не вызывается:
  0,34–0,35 c. Туннель AmneziaWG на это не влияет.
- **Хвост 9–14 c** — ответы, где модель делает 3–4 обращения: реплика «всё сразу», замена позиции,
  уточнение неоднозначного названия. В 90 % случаев время ответа ≤ 10 c.
- Полный заказ из 6 реплик — около 30 c суммарно, но клиент ждёт не всё сразу, а по одному ответу.

## Что уменьшит время ответа (по эффекту)

1. **Меньше обращений к модели.** Типовой ответ — «позвал `set_items` → прочитал сводку → ответил».
   Если инструмент сразу отдаёт сводку, вместо трёх обращений остаётся два: −2,2 c к каждому ответу.
2. **Короче история в prompt.** `DIALOG_HISTORY_LIMIT=6` → 4: уточнения и так живут в состоянии,
   а не в истории; каждый запрос становится дешевле.
3. **Кэш меню в процессе.** `get_menu` тянет 998 строк прайса из БД на каждое обращение; кэш на 30–60 c
   с инвалидацией по времени экономит 50–150 мс на запрос.
4. **Статусы в черновике** уже включены (`TELEGRAM_DRAFT_STREAM=1`): «Думаю… → Ищу в меню…».
   Время ответа не меняют, но пауза перестаёт читаться как зависание.
