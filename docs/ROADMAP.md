# Этапы порта (каждый закрывается проверкой)

Правило: этап считается закрытым только когда все проверки этапа зелёные и результат приложен
к отчёту. Python-проект (`D:\agentic_food_order`) — эталон, не меняется, используется для сверки.
Тестовые данные в БД оставляем как есть (меню есть только у кафе 3 — на нём и проверяем).

## Этап 0 — окружение и ядро (готово)

Конфиг, подключение кода каркаса как библиотеки, запись заказа, меню/кафе, проверка окружения.

Проверка: `npm run check:feedmer`, `npm run smoke:order`, `npm run smoke:menu`, `npm test`.

## Этап 1 — состояние заказа и инструменты, без LLM (в работе)

Порт `domain/models.py` + `tools/order_agent_tools.py` + `tools/menu.py`:
состояние черновика, 11 инструментов, разрешение позиций по меню, нормализация телефона,
сводка/подтверждение/отмена, отправка заказа через `createPickupOrder`.

Проверка:
* `npm test` — юнит-тесты инструментов и состояния (в том числе «submit вызывает каркас один раз»);
* `npm run smoke:tools` — скриптовая «беседа» без LLM: позиции → точка → время → оплата → телефон →
  сводка → подтверждение → заказ в БД кодом каркаса → уборка; печатает созданный заказ.

## Этап 5 — статусы хода в черновике сообщения

Цель: не оставлять клиента с пустым экраном, пока агент работает. Логика хода при этом не меняется —
меняется только то, что видно в чате.

Сделано: `src/bot/draftStream.js` (`sendMessageDraft`, один `draft_id` на ход, словарь `STATUS_LABELS`,
троттлинг 400 мс, дедуп текста, обрезка до 4096, гашение стрима по любой ошибке API). Агент сообщает
только имя инструмента через необязательный `onProgress` (`src/llm/orderAgent.js`), в человеческий статус
его переводит бот; `service.handleText` и `orchestrator.handleMessage` просто пробрасывают колбэк.
Финальный ответ по-прежнему `ctx.reply` с клавиатурой: черновик исчезает сам. Флаги —
`TELEGRAM_DRAFT_STREAM` (по умолчанию вкл) и `TELEGRAM_DRAFT_INTERVAL_MS`.

Отказ от настоящего стрима токенов (осознанно): финальный текст приходит не в `content`, а в
JSON-аргументах `respond_to_customer`, поэтому SSE-стрим требует инкрементального парсинга частичного
JSON и второго пути в агенте ради ~1 с выигрыша на ответе в 1–3 предложения. Статусы дают тот же
эффект «бот работает» без риска для tool-calls.

Проверка: `npm test` — 65/65 (новые: `test/draftStream.test.js`, `test/botDraft.test.js`, статусы в
агенте и проброс в сервисе). `npm run smoke:draft` — живой вызов API: пять статусов приняты Telegram
(`true`), финальное сообщение заменило черновик в чате `ADMIN_TELEGRAM_ID`.

### Правки по фидбэку владельца (01.11.2026)

Две жалобы с живого просмотра — обе про то, как черновик выглядит в Telegram Desktop,
поведение агента не менялось:

1. **Точки дублировались** («Ищу в меню…» + клиентские бегущие точки). Убрали `…` из всех подписей
   `STATUS_LABELS`; тест `подписи без многоточия` держит это правило.
2. **Пузырь со статусом оставался в чате после ответа.** Проверили живьём на четырёх вариантах:
   `draft → sendMessage` (остаётся пузырь со статусом), `draft → пустой draft → sendMessage`
   (остаётся пузырь «...»), `draft → сообщение → пустой draft` (то же), `draft без text` (то же),
   `draft с ТЕКСТОМ будущего ответа → sendMessage` (**один пузырь, ничего лишнего**). Вывод:
   клиент заменяет черновик сообщением, только когда их текст совпадает; иначе держит черновик
   до 30 с. Поэтому `withDraft` перед отправкой ответа ставит в черновик сам ответ
   (`DraftStream.setText`), и только потом бот шлёт сообщение с клавиатурой — побочный плюс:
   текст появляется в чате как «печатается», а не возникает целиком.

Проверка: `npm test` 68/68; `npm run smoke:draft` — боевой путь `withDraft` в чате
`ADMIN_TELEGRAM_ID`, в чате остаётся одно сообщение без статусной строки (сверено скриншотом).


## Этап 6 — читаемость ответов: структура вместо простыни

Проблема сформулирована владельцем как «теряются переносы и форматирование». Проверка живого чата
через Telethon показала другое: транспорт переносы не режет (40 сообщений — все с «•» с новой строки),
но модель нестабильно пишет прозу вместо блоков, а в живых ответах встречались строки на 117–150
символов. Отдельно выяснилось, что прежний вывод «38/38 ответов плоские» был артефактом бенча:
`_clip()` в `runner.py` склеивал `\n` в пробел при записи отчёта.

Сделано:
- `src/bot/format.js` — детерминированный форматтер (плоский текст, без parse_mode): «•» в начало
  строки, поля заказа на свою строку, пустая строка перед «Итого»/вопросом/«Варианты:» и после списка,
  схлопывание пробелов и пустых строк. Ничего не перефразирует, цены и названия не трогает.
- `src/llm/prompt.js` — блок «Финальный ответ» переписан в жёсткий контракт (статус → список → поля →
  итог → вопрос) + четыре эталонных примера; запрещены «• A • B», списки через запятую и состав
  заказа в прозе.
- `BotService.handleText` применяет форматтер до `ensureChoicesInText`; сопоставление подписей кнопок
  стало пословным («да» больше не находится внутри «Стандарт», дежурная фраза про «нет» исключается) —
  раньше в блок попадала одна кнопка из двух.
- Уведомление админу заполняется по снимку `submit_order` (раньше `state` уже был очищен и в письме
  стояли пустые «Позиции:/Самовывоз: —»), плюс пустая строка перед «Итого».
- В бенче близнеца починен `_clip()`: отчёты сохраняют переносы строк, формат стал проверяемым.

Проверка: `npm test` — 77/77 (новые `test/format.test.js`, тесты сервиса на структуру и на кнопки,
снимок заказа в агенте). Живой прогон бенчем (`docs/parity/format-check.json` — `happy_shaurma`,
`docs/parity/format-check2.json` — `stepwise_slots`): максимальная длина строки 36–59 символов вместо
117–150, списки и блоки на месте, «Варианты: • да • нет» полные. `ok=False` в этих отчётах — прежнее
расхождение ожиданий бенча («подтверд|подтверж» против «Всё верно?»), не формат.
