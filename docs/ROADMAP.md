# Этапы порта (каждый закрывается проверкой)

Правило: этап считается закрытым только когда все проверки этапа зелёные и результат приложен
к отчёту. Python-проект (`D:\agentic_food_order`) — эталон, не меняется, используется для сверки.
Тестовые данные в БД оставляем как есть (меню есть только у кафе 3 — на нём и проверяем).

## Этап 0 — окружение и ядро (готово)

Конфиг, подключение кода каркаса как библиотеки, запись заказа, меню/кафе, проверка окружения.

Проверка: `npm run check:feedmer`, `npm run smoke:order`, `npm run smoke:menu`, `npm test`.

## Этап 1 — состояние заказа и инструменты, без LLM (в работе)

Порт `domain/models.py` + `tools/order_agent_tools.py` + `tools/menu.py`:
состояние черновика, 11 инструментов, разрешение позиций по меню, нормализация телефона,
сводка/подтверждение/отмена, отправка заказа через `createPickupOrder`.

Проверка:
* `npm test` — юнит-тесты инструментов и состояния (в том числе «submit вызывает каркас один раз»);
* `npm run smoke:tools` — скриптовая «беседа» без LLM: позиции → точка → время → оплата → телефон →
  сводка → подтверждение → заказ в БД кодом каркаса → уборка; печатает созданный заказ.

## Этап 2 — LLM-агент и оркестрация (код готов, ждёт ключ для живой проверки)

`llm/client.js` (OpenAI / DeepSeek / Ollama через fetch), `llm/prompt.js` (системный промпт 1:1 из
эталона), `llm/orderAgent.js` (tool-loop, `respond_to_customer`, восстановление ответа, лимит раундов),
`bootstrap/orchestrator.js` (таймаут хода, извинение при ошибке), `state/sessions.js` (история диалога).

Проверка:
* `npm test` — 9 детерминированных тестов агента и оркестратора на подменённой модели (без сети);
* `npm run smoke:agent` — живая переписка с моделью и заказ в БД (нужен ключ в `.env`; без ключа скрипт
  завершается с понятным сообщением).

Статус: код и тесты зелёные (31/31), живой прогон не выполнен — нет ключа в `.env`.

## Этап 3 — Telegram-бот (код готов; ручная проверка ждёт свободный токен)

`bot/service.js` (порт `bot/handlers/*` эталона: /start, /cancel, блокировка хода, история,
уведомление админа), `bot/telegram.js` (тонкий слой telegraf, reply-кнопки как в эталоне),
`index.js` (npm start).

Проверка:
* `npm test` — 8 тестов сервиса (старт/отмена/блокировка/история/уведомление), всего 39;
* `npm run smoke:bot` — диалог через тот же сервис, что у telegraf: заказ 284860 в БД + payload
  уведомления админа;
* `npm start` — бот авторизуется (@testfeedmer_bot), но получает 409: токен слушает другая копия.

Статус: **закрыт**. Живая проверка владельцем в Telegram (@testfeedmer_bot) — заказ `284861`
(кафе 68, 12.10.2026 12:40, наличными, «Круассан с шоколадом и миндалем», 60 ₽).

Проверка этапа вскрыла дефект: позиция была набрана из меню кафе 3 (меню по умолчанию, пока точка
не выбрана), а заказ ушёл в кафе 68 — в общей БД заказ одного кафе содержал блюдо другого.
Исправлено: `set_pickup_point` перепроверяет состав по меню выбранного кафе (недоступные позиции
снимаются с заказа, агенту возвращается `dropped_items` + `note`), тест «смена точки перепроверяет
состав по меню нового кафе». Дополнительно в `.env` задан `ORDERS_DEFAULT_CAFE_ID=68` — меню по
умолчанию берётся у реального кафе, а не у демо.

## Этап 4 — паритет с Python-эталоном и деплой

Прогон одних и тех же сценариев на Node и на Python, сравнение созданных заказов и текстов ответов;
документ `docs/PARITY.md` с результатами и известными отличиями; инструкция деплоя (чекаут FeedMer
рядом, фиксированный коммит, `check:feedmer` в pre-start).

Подготовка данных (сделано): прайсы кафе 68 (155 позиций) и 72 (65 позиций) залиты в тестовую БД
штатным писателем каркаса `db.updatePricelist` — из таблиц кафе, лист «Общий справочник»
(`npm run seed:pricelist [cafeId …]`). Для этого в тестовой БД добавлена колонка `pricelist.status`
(каркас пишет 9 колонок, включая `status`; миграции FeedMer её не создают — в `scripts/fix-shared-db-schema.sql`).
Проверка: `check:feedmer` 19/19, сквозной диалог через сервис бота — заказ `284862` в кафе 68
(«Куриная Стандарт 320г» ×2 по 340 ₽ = 680 ₽) из залитого прайса.
