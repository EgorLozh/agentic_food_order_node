# Паритет с Python-эталоном: E2E-прогон сценариев через Telegram

Проверка этапа 4: одни и те же сценарии прогоняются через **тот же штатный E2E-бенч эталона**
(`food-order-bench`, Telethon, отдельный тестовый аккаунт) сначала по Python-боту, потом по нашему
Node-боту. Бот один и тот же — `@testfeedmer_bot` (общий `BOT_TOKEN`), общая БД `testing`.

## Как прогоняли

```
# эталон (питон-бот с уведомлением админа, чтобы submit-ход видел «Новый заказ» в чате админа)
cd D:\agentic_food_order
ORDER_SINK=both ./.venv/Scripts/python.exe -m food_order.main

# наш бот
cd D:\agentic_food_order_node
npm start                      # ADMIN_TELEGRAM_ID=8862284665, ORDER_NOTIFY_ADMIN=1

# прогон сценариев (по очереди под каждый запущенный бот)
cd D:\agentic_food_order
./.venv/Scripts/python.exe -m food_order.bench.cli run --label <имя> \
  --scenarios <каталог сценариев> -o <отчёт.json>
./.venv/Scripts/python.exe -m food_order.bench.cli compare <отчёт.json> <отчёт.json>
```

Тестовый аккаунт бенча (Telethon-сессия `bench.session`) — id `8862284665`, он же `ADMIN_TELEGRAM_ID`,
поэтому и ответ клиенту, и админское «Новый заказ» приходят в один чат: сценарий submit ждёт
`await_replies: 2`.

### Два набора сценариев

* **Оригинальные** (`D:\agentic_food_order\config\scenarios`) — как есть, не менялись.
* **Копия для сравнения** (`docs/parity/scenarios`) — 9 сценариев эталона с одним ослабленным
  регэкспом: `(подтверд|подтверж)` → `(подтверд|подтверж|верно|правильно)`.
  Причина: бот (оба — и эталон, и наш) на сводке спрашивает «Всё верно?», а не «Подтвердите», и это
  единственное, на чём валится 5 из 9 сценариев. Оригинальный набор оставлен и прогнан тоже —
  он служит базовой линией.

## Расхождения и дефекты, найденные этим прогоном

1. **`chatids.telegram_chatid` объявлен как `int` в миграциях FeedMer.** Идентификаторы Telegram
   давно превышают int32 (аккаунт бенча `8862284665`), из-за чего регистрация такого клиента падала
   с `value out of int32 range` — заказ не создавался **ни нашим ботом, ни эталоном**.
   В тестовой БД колонка расширена до `BIGINT` (`scripts/fix-shared-db-schema.sql`, пункт 6).
   Для прода это правка схемы обязательна, иначе новые клиенты Telegram не смогут заказать.
2. **Уведомление админа приведено к формату каркаса** — `Новый заказ ORD-<pk_orders>`, клиент,
   позиции, точка с адресом, время, оплата, телефон, итог (`src/bot/service.js`,
   `adminOrderText`). Иначе submit-ход сценариев не проходит: они проверяют «Новый заказ» и «ORD-».
3. **`pricelist.status`** — каркас пишет прайс 9 колонками, включая `status`, которой в схеме нет:
   без неё штатный синк прайса молча падал. Добавлена тем же скриптом.

## Правки по фидбэку с тестирования (живой прогон владельцем в Telegram)

| что просили | что сделано |
|---|---|
| в сообщении со всеми разделами меню | разделы перечисляются и в тексте (списком с новой строки), и кнопками: правило в промпте + код-гарантия `ensureChoicesInText` |
| «печатает…» не всё время ответа | `withTyping` в `src/bot/telegram.js`: chatAction отправляется сразу и обновляется раз в 4 с (Telegram гасит его через ~5 с); покрыто тестом |
| кнопка «Главное меню» на каждом шаге, «Новый заказ» после заказа | reply-клавиатура всегда содержит «Главное меню», после оформления — «Новый заказ»; «Главное меню» не теряет черновик, «Новый заказ» сбрасывает |
| добавки были только текстом, без цен и кнопок | лимит кнопок 8 → 20 (позиции категории больше не выпадают); в тексте позиции с ценами |
| добавки можно было добавить без шаурмы | `set_items` отклоняет заказ только из добавок: «Соусы и добавки идут только к основному блюду» + подсказка спросить блюдо |
| текст слитный, без отступов | блоки через пустую строку, позиции и варианты списком «•», сводка заказа отдельными строками (правило + пример в промпте) |
| варианты при уточнении только в кнопках | варианты дублируются в тексте (п.1 и п.6 — одна и та же гарантия) |

Дополнительно прогон вскрыл баг, которого в фидбэке не было: **неоднозначная точка кириллицей**
(«Куриная Стандарт на Ракете к 14:00») не распознавалась — инструмент отвечал «точка не найдена», и
модель молча выбирала кафе по умолчанию, вместо вопроса «какая из двух». Исправлено сравнением с
транслитерацией и терпимостью к падежам (`«Ракета» ↔ «Raketa»`, `«Ракете» → rakete ≈ raketa`) —
вторым проходом, прямое сравнение не тронуто. Это и дало 9/9 вместо 8/9.
